#+DATE: 2026-10-22
#+TODO: TODO IN-PROGRESS BLOCKED | DONE CANCELLED

How WebGPU could speed up WindNinja's mass-consistent solver, especially in
the browser (WebAssembly). Builds on the momentum work in
[[file:WEBGPU_PLAN.org][WEBGPU_PLAN.org]] and on jessie-fire-simulation's
=cljs-webgpu= layer (=../jessie-fire-simulation/cljs-webgpu/=).

* Summary
- The mass solve is one sparse, symmetric positive-definite linear system per
  run, which suits the GPU well.
- The gain is larger in the browser than natively, because WebAssembly CPU
  code is slower there.
- The bigger opportunity is systemic: wind could flow straight into
  jessie-fire-simulation's GPU fire spread without leaving the GPU.
  =FARSITE_GPU.org= currently rules gridded WindNinja winds out of the browser
  ("could be imported as precomputed rasters"); that limit would go away.

* Baseline
- *The system*: finite elements (8-node hexahedra) on the terrain-following
  mesh, a 27-point stencil, symmetric positive-definite, stored as the upper
  half in CSR.
  - Equation: ∂x(Rx ∂Φ/∂x) + ∂y(Ry ∂Φ/∂y) + ∂z(Rz ∂Φ/∂z) + ∇·u₀ = 0, with
    Rx = Ry = 1/(2αh²) and Rz = 1/(2αv²).
  - Velocity recovery: u = u₀ + Rx ∂Φ/∂x, and likewise for v and w.
  - Φ = 0 on the sides and top; the ground is impermeable (natural BC).
- *The solver*: conjugate gradient preconditioned with SSOR (an inherently
  sequential smoother; Jacobi fallback, then MINRES), stopping when the
  relative residual ‖r‖₂/‖b‖₂ is 0.1 (52–57 iterations on Big Butte; see
  0.1).
- *Native speed* (Big Butte, 8 threads, linear solve dominates):

  | mesh   | DEM × layers | nodes | solve  | total  |
  |--------+--------------+-------+--------+--------|
  | coarse | 61×66×20     | ≈80k  | 0.15 s | 0.18 s |
  | medium | 97×104×20    | ≈200k | 0.37 s | 0.43 s |
  | fine   | 137×147×20   | ≈400k | 0.75 s | 0.85 s |

- *In the browser*: WebAssembly runs single-threaded unless the page is
  cross-origin isolated, and without native vectorisation. The same solve is
  likely several seconds there (an estimate, not measured).
- *Not ported yet*: the WASM module (=src/ninja/gpu/wasm/=) holds only the
  RANS momentum solver, not the mass solver.

* Ways WebGPU could speed it up
** 1. Keep the whole conjugate-gradient loop on the GPU, with no readbacks
- *Per-iteration work*: one sparse matrix-vector product, two dot products
  and three vector updates.
- *The real cost is waiting*: measured on this branch, a dispatch costs about
  23 µs but a wait costs 0.2–0.5 ms. A naive port that reads α, β and the
  residual back each iteration would be wait-bound.
- *Fix*: compute α and β in a tiny single-thread kernel that writes them to a
  buffer the next kernels read, and check convergence only every N
  iterations.
- *Stopping without asking the CPU*: jessie's eikonal (FIM) solver already
  uses the trick: =dispatchWorkgroupsIndirect= with a GPU-written workgroup
  count. A convergence kernel can write zero workgroups once the residual is
  below tolerance.
- Consider pipelined CG variants (one fused reduction per iteration) if
  dispatch count dominates.

** 2. Treat the matrix as a structured 27-point stencil
- *Layout*: the mesh is a regular rows × columns × layers grid, so store the
  coefficients per node in packed structure-of-arrays slots, as =gpu::Grid=
  does. Since the matrix is symmetric, 14 of the 27 are enough.
- *Size*: about 22–43 MB at 400k nodes, within the 128 MiB default limit per
  binding.
- *The multiply* becomes a gather over neighbours, with no indirection arrays.
- *Assembly* can move to the GPU too. Per-element stiffness integration is
  fully parallel; summing into nodes can use the race-free gather pattern
  from the RANS kernels, or jessie's compare-and-swap float trick
  generalised from minimum to addition.

** 3. Swap the preconditioner
SSOR doesn't parallelise, so it has to go.
- *Jacobi*: trivial on the GPU, and WindNinja already has it as a fallback.
  The first step.
- *Multicolour Gauss-Seidel / SSOR*: 8 colours for a 27-point stencil, so
  each colour updates in parallel.
- *Geometric multigrid as a preconditioner* on the structured mesh: near
  constant iteration counts. The RANS work showed small coarse levels are
  dispatch-bound, so use few levels, or solve the coarsest on the CPU.

** 4. Precision: f32 with targeted df64
WGSL has no 64-bit floats. Plain 32-bit CG on 400k unknowns can lose
accuracy in its long dot products. =cljs-webgpu= already has the remedy:
- *Selective precision*: guarded df64 (~48-bit, about 4–6× the cost of f32)
  only for the dot products and residual sums, not the whole solve.
- *Mixed-precision refinement* (recommended in =cljs-webgpu/PLAN.org=): solve
  in f32 on the GPU; compute an outer residual correction in df64 or on the
  CPU.
- *The guard is mandatory*: without =bitcast(x ^ params.zero)=, Apple's
  Metal compiler reassociates the arithmetic and df64 comes out worse than
  f32.

** 5. Fuse the pipeline, and hand the wind to the fire model on the GPU
- *The pipeline*: initial log-profile field, divergence right-hand side,
  solve, velocity from ∇Φ, outputs. All per-node or per-element, so all of it
  can stay on the GPU.
- *Hand-off*: pass the u and v buffers directly to jessie's GPU fire-spread
  kernels (Rothermel, FIM), with no download and re-upload.
- *One shared device*: buffers can't cross devices, so the WASM module and
  the page must use the same =GPUDevice=. emdawnwebgpu can import a
  JavaScript-created device.

** 6. Batch and warm-start repeated solves
That's where the time adds up:
- point initialization repeats the solve up to 150 times to match stations;
- forecast time series and diurnal runs solve once per time step;
- fire-scenario ensembles solve once per wind direction.

Two things help:
- start each solve from the previous Φ instead of zero;
- solve several right-hand sides at once (e.g. 8 directions in one pass): the
  matrix is the same, so one stencil read serves 8 vectors, a clear win for a
  bandwidth-bound kernel.

* Expected gain (estimates, to be measured)
- *Per iteration* at 400k nodes: about 50 MB of memory traffic, roughly
  0.3 ms at M3-class bandwidth, plus 4–6 dispatches.
- *Whole solve*: with a few hundred Jacobi-preconditioned iterations, about
  0.1–0.3 s.
- *Compared with*: native CPU about 0.75 s; WebAssembly in the browser likely
  several seconds.
- *Upshot*: maybe 10–30× in the browser and 2–5× natively, more for repeated
  solves. The Jacobi iteration count decides most of this, so measure it
  first (Phase 0).

* Which code to build on
- *C++ path (this branch)*: extend =windninja_wasm= with the mass solver.
  First extract the mesh and FEM assembly into core-free code, as was done
  for RANS (=TerrainGrid=, =SolveDemOnGpu=). Reuses =gpu::Buffer=,
  =gpu::Reducer=, the race-free pattern and the test discipline, and can be
  tested against native WindNinja.
- *ClojureScript path (=cljs-webgpu=)*: its =linalg= already provides =axpy!=,
  =dot=, =nrm2= and df64. A Jacobi-preconditioned CG is mostly those calls
  plus one stencil multiply kernel that it lacks. Lives next to the fire
  simulation, which simplifies sharing one device.
- *Hybrid*: the C++ module as the correctness reference (as the hill
  self-test does for RANS), whichever runtime the app prefers in production.

*** Results (2026-10-22, M3 Max, Big Butte, 10 mph from 270, domain average)
=scripts/mass_solver_timing.sh <cli> big_butte.tif=; times in seconds.

| mesh   |  nodes | precond | iters | solve 8 thr | solve 1 thr | total 8 thr |
|--------+--------+---------+-------+-------------+-------------+-------------|
| coarse |  78000 | SSOR    |    52 |        0.17 |        0.17 |        0.20 |
| coarse |  78000 | Jacobi  |   125 |        0.13 |        0.15 |        0.16 |
| medium | 197760 | SSOR    |    55 |        0.39 |        0.43 |        0.44 |
| medium | 197760 | Jacobi  |   147 |        0.31 |        0.44 |        0.37 |
| fine   | 397120 | SSOR    |    57 |        0.84 |        0.93 |        0.95 |
| fine   | 397120 | Jacobi  |   158 |        0.69 |        0.93 |        0.79 |

Findings:
- *Few iterations*: 52–57 with SSOR, 125–158 with Jacobi, growing slowly
  with mesh size. Iteration count is not the problem; cost per iteration is.
- *Slow iterations*: fine Jacobi is ~4.3 ms per iteration at 400k nodes.
  A GPU iteration should be ~0.3 ms of memory traffic plus ~0.15 ms of
  dispatches.
- *The CPU solve barely uses threads*: 1 thread is only 0–35% slower than 8.
  SSOR's triangular solves are sequential, and the symmetric upper-half CSR
  product doesn't parallelise well. So single-threaded WebAssembly loses
  little to the thread count; it loses to wasm overhead instead (not
  measured yet).
- *Jacobi is already faster than SSOR on the CPU* (8 threads): 2.7× the
  iterations, but cheaper ones. Its answer differs from SSOR's by 0.015 mph
  RMSE, 0.27 mph max, on a 9.9 mph mean (fine mesh); both stop at the same
  tolerance, so this is solver-tolerance noise, not a defect.
- *The stopping test is relative*: =resid = ‖r‖₂ / ‖b‖₂ ≤ 0.1=, not the
  absolute 2-norm the comment in =ninja.cpp= suggests.
- *Rough GPU estimate* (fine, Jacobi): 158 × ~0.45 ms ≈ 0.07 s plus
  readbacks every 10 iterations (~5 ms) ≈ 0.08 s, against 0.69 s native
  (≈9×) and probably 1–3 s in single-threaded WebAssembly (≈15–35×).

* Phase 1: Core-free mass solver (no behaviour change)
** DONE 1.1 Extract assembly, solve and velocity recovery from =ninja= [6/6]
Design (2026-10-22):
- =mass_fem.{h,cpp}= (no GDAL, no =ninja=, no =Mesh=):
  - =MassGrid=: =ncols=, =nrows=, =nlayers= and node coordinates x/y/z, node
    =n = col + ncols*(row + nrows*layer)= (the =Mesh= / =wn_3dArray= order,
    so fields pass as plain pointers);
  - =AssembleMass(grid, u0, v0, w0, alphaV, alphaH)= → =MassSystem= (upper
    CSR =SK=, =col_ind=, =row_ptr=, =RHS=), Dirichlet rows applied;
  - =RecoverVelocity(grid, phi, u0, v0, w0, alphaV, alphaH, u, v, w)=.
  - The element math is the one-point quadrature hexahedron that =element=
    uses (=NUMQPTV=1=: one point at the centre, weight 8), copied with the
    same arithmetic order.
- =mass_pcg.{h,cpp}=: the PCG from =ninja::solve()= with its BLAS helpers,
  progress and cancel as callbacks.
- =mass_grid_mesh.cpp=: =MassGrid::FromMesh(const Mesh&)= (like
  =rans_grid_mesh.cpp=), the only part that sees =Mesh=.
- =ninja::discretize()= keeps the stability → =alphaVfield= step and calls
  =AssembleMass=; =setBoundaryConditions()= folds into it;
  =computeUVWField()= calls =RecoverVelocity=; =solve()= calls the PCG.
- Note: assembly sums with =omp atomic= and velocity recovery merges
  per-thread sums in a =critical= section, so the last bits depend on
  thread timing. Compare runs at =num_threads = 1= for byte identity, and
  with a tolerance otherwise.

=wn_3dScalarField::ComputeGradient= (around line 514) repeats the
inverse-distance "stress smoothing" now in =RecoverVelocity=. Could call a

** TODO Run-to-run nondeterminism in the mass solver with threads
Assembly sums with =omp atomic= and velocity recovery merges per-thread
sums in a =critical= section, so multi-threaded results can differ in the
last bits between runs (not seen on Big Butte fine). A deterministic
gather (as in the GPU kernels) would fix it.
** TODO Solver comment says "2-norm of residual"; it is relative to ‖b‖
=ninja.cpp= (=stop_tol=): the test is ‖r‖₂/‖b‖₂ ≤ 0.1.
** TODO MINRES fallback is unreachable
=ninja::solve()= returns true or throws, never false, so
=if(solve(...)==false) solveMinres(...)= never runs. =solveMinres()= and the
=ninja::cblas_*= / =mkl_*dcsrmv= helpers (~350 lines) exist only for it.
Either delete them or make a non-converged CG fall back to MINRES as
intended (ask RJ which).
** TODO Half of the CPU matrix-vector product is serial
The symmetric upper-triangle product (=SymmetricMultiply=, formerly
=ninja::mkl_dcsrmv=) scatters each row's transpose in a serial loop, which
is why the solve barely speeds up with threads (0.1). Storing the full
matrix (or the 27-point stencil, as Phase 2 does on the GPU) would let the
CPU product run fully in parallel too.
