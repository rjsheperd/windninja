Companion to [[file:WEBGPU.org][WEBGPU.org]] (findings and rationale). This file turns
those findings into phases, tasks, subtasks and tests.

* Conventions
- *Tests*:
  - Unit tests are Boost.Test cases in =autotest/= and are added to =test_main=.
  - Each case is registered with =add_test(<suite>_<case> ... --run_test=<suite>/<case>)=,
    matching the existing =autotest/CMakeLists.txt= style.
  - CLI integration tests are =.cfg= files under =autotest/config/pass/=.
- *Golden comparison*: compare to the OpenFOAM-11 reference outputs from
  Phase 0. The metrics are:
  - speed: RMSE and max abs diff, in m/s;
  - direction: circular mean abs diff, in degrees;
  - k: relative RMSE.
- *Tolerances*: placeholder values are marked =TBD=. They need sign-off from
  the WindNinja science team before Phase 2 ends.
- *Gates*: =GATE= headings are go/no-go decisions. Don't start the next phase
  until the gate is recorded as DONE or CANCELLED, with a note.

* Phase 2: CPU reference structured RANS (=CpuRansBackend=)
Goal: prove the numerics on the CPU, where debugging is cheap, before any GPU
work. This also becomes the oracle for the GPU kernels.

** TODO 2.1 Grid and metrics on the mass-solver =Mesh=
- [ ] Build a =Mesh= from the =MomentumProblem= (=buildStandardMesh=). Pick
      layers and vertical growth to hit the cell budget.
- [ ] Compute the cell-centred finite-volume metrics: cell volumes, face area
      vectors and the transformation Jacobian. Use local coordinates (UTM
      minus the domain origin).
- [ ] Compute wall distance for each cell (needed by the wall functions and
      the log-law initialisation).
*** Tests
- =rans_metrics_flat_box=: on a flat DEM, the volumes sum to the box volume
  and face areas match Δx·Δy (1e-12 relative).
- =rans_metrics_closed_surface=: for each cell, the face area vectors sum to
  zero (geometric conservation law) on a terrain mesh.
- =rans_metrics_sine_hill=: the total volume matches analytic integration of a
  sinusoidal hill, within discretisation error.

** TODO 2.2 Laminar incompressible solver (pseudo-compressibility)
- [ ] Use the artificial-compressibility formulation with local pseudo time
      stepping.
- [ ] Use second-order upwind convection, central diffusion, and Rhie-Chow
      style pressure dissipation.
- [ ] Add boundary conditions: velocity inlet, pressure outlet, slip top, no
      slip / wall.
*** Tests
- =rans_mms_laminar=: a manufactured solution on a curvilinear grid shows the
  observed order of accuracy at least 1.8 for u and at least 1.5 for p, over 3
  grid levels.
- =rans_lid_cavity_re100=: centreline velocities are within 2% of the Ghia
  et al. (1982) reference.
- =rans_converges_residual=: the residuals fall 5 orders of magnitude within
  =TBD= iterations on the cavity.

** TODO 2.3 RNG k-ε with atmospheric wall functions
- [ ] Add the transport equations for k and ε with the RNG coefficients from
      =data/ninjafoam/11/constant/momentumTransport=.
- [ ] Port the rough-wall function from
      =src/ninjafoam/11/wallBC/nutkAtmRoughWallFunction=.
- [ ] Port the log-profile inlets for U, k and ε from
      =src/ninjafoam/11/inletBC=, and the log-law initialisation from
      =applyInit=.
- [ ] Assign inlet and outlet sides by wind direction, as =SetInlets= does today.
*** Tests
- =rans_flat_terrain_log_law=: over a flat DEM the profile stays log-law along
  the whole fetch (homogeneous ABL), with speed at 10 m AGL within 2% of
  analytic at inlet, middle and outlet.
- =rans_wall_function_ustar=: on flat terrain, the recovered u* matches
  U∞κ/ln(h/z0) within 1%.
- =rans_bc_port_matches_openfoam=: the inlet U, k and ε face values match the
  OpenFOAM BC code at the same heights (1e-10 relative; it's the same formula).

* Phase 4: GPU solver port (=WebGpuRansBackend=)
Goal: the same numerics as the =CpuRansBackend=, as WGSL kernels.

** TODO 4.1 Data layout and precision
- [ ] Use a structure-of-arrays layout for the fields (u, v, w, p, k, ε, ν_t)
      and the metrics on the (i,j,k) grid.
- [ ] Use f32 throughout, with coordinates kept local to the domain origin.
- [ ] Reduce residuals with a pairwise / two-pass sum to limit f32 error.
*** Tests
- =gpu_reduction_sum=: summing 10M values matches f64 CPU within 1e-6
  relative.
- =cpu_rans_f32_mode=: the CPU backend compiled with float gives golden results
  within tolerance. This shows f32 is adequate before blaming kernels.

** TODO 4.2 Kernels, one per solver stage
- [ ] Gradients / reconstruction.
- [ ] Convective and diffusive fluxes.
- [ ] Pseudo-compressibility update with local Δτ.
- [ ] k-ε source terms and the wall-function cells.
- [ ] Boundary conditions: inlet log profiles, outlets, top, ground.
- [ ] Residual norms.
*** Tests
For each kernel, a =gpu_kernel_<stage>_matches_cpu= test:
- run one stage on a random field on the Big Butte coarse mesh;
- compare against =CpuRansBackend= with f32;
- require max relative diff 1e-5 (=TBD=).

** TODO 4.3 Geometric multigrid
- [ ] Coarsen the structured grid (2× in i, j and k where possible), with
      restriction and prolongation kernels.
- [ ] Use a V-cycle around the pseudo-time smoother.
*** Tests
- =gpu_multigrid_poisson=: an analytic Poisson problem converges at a rate
  that doesn't depend on grid size (rate within 10% across 3 grid sizes).
- =gpu_multigrid_speedup=: the cavity reaches the 2.2 residual target in at
  least 3× fewer fine-grid sweeps than single-grid.

** TODO 4.4 End-to-end GPU backend
- [ ] Host loop: iterate until converged or out of iterations, read back
      residuals every N steps, and honour =checkCancel=.
- [ ] Read back the output-height sample and the optional 3-D fields.
*** Tests
- =momentum_gpu_golden_*=: all golden cases are within the GATE 0 tolerances
  of OpenFOAM, *and* within a tighter tolerance of the CPU backend.
- =momentum_gpu_cancel=: cancelling mid-run returns promptly (under 1 s) and
  leaks no GPU memory (device memory is stable over 10 cancelled runs).
- =momentum_gpu_deterministic=: two runs on the same device are bitwise
  identical. If not, document the non-determinism and use a tolerance.

** TODO GATE 4: GPU backend fit for integration
- Golden cases pass on at least one GPU from each vendor available to the team
  (Apple, NVIDIA, AMD, Intel).
- Runtime beats OpenFOAM on the 100k-cell case on a laptop discrete or
  integrated GPU.

* Out of scope / later
- Browser build. It needs either WindNinja core in WASM (GDAL etc.) or a
  solver-only web component. Decide after GATE 4, and keep the WGSL free of
  native-only assumptions so either stays possible.
- LBM / LES transient solver (see WEBGPU.org, "Why not LBM").
- Non-neutral stability, Coriolis, or spatially varying inflow. These become
  possible once the solver is in-house, but need separate validation.
